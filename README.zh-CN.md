# ReportFlow｜专业研究报告工作流

**专业研究报告的工作流**

让 AI 不只是“写报告”，而是按照真正的研究流程工作。

> 先想清楚，再研究清楚，最后讲清楚。

从问题定义、证据搜集、分析与写作，到逐章审核和最终出版，ReportFlow 把复杂研究拆成一套可追踪、可恢复、可验证的工作流。它适合 AI 研究、AI 写研究报告、行业研究、公司研究、竞品分析和市场研究。

## ReportFlow 是什么？

**先想清楚，再研究清楚，最后讲清楚。**

ReportFlow 不是一个让 AI 帮你写报告的提示词，也不是换标题就能套用的固定模板。它会先问清楚读者要做什么决定，再建立匹配问题的研究架构，把重要判断连接到具体证据，经过逐章审核，最后检查真正交付的 HTML 和 PDF。

具身智能只是一个参考案例，ReportFlow 也适用于市场进入和投资主题研究，并提供证据追踪、证据管理、长报告审核和 PDF 报告出版能力。

## 为什么需要 ReportFlow？

普通 AI 报告常常在问题尚未定义清楚时就开始写作；找到一条引用就把结论说得过满；用流畅文字掩盖缺少的数据；所有项目套用同一套章节；PDF 导出后便宣布完成。

ReportFlow 把这些容易被忽略的工作变成检查点：明确范围和证据需求，保留未知（Unknown）、存在争议（Disputed）和披露不足（Disclosure Gap），记录结论与来源的对应关系，并在关键前提变化时重新检查受影响章节。它是一套面向 Codex Skill 的研究工作流，而不是单纯的 AI 写作工具。

**研究深度可以不同，但证据标准不能降低。**

## 普通 AI 报告与 ReportFlow

| 普通 AI 报告 | ReportFlow |
| --- | --- |
| 从宽泛主题直接开始写 | 先明确决策、受众和研究问题 |
| 有引用就算支撑充分 | 检查结论是否真的被证据支持 |
| 缺失信息被写成确定判断 | 保留未知、争议和披露不足 |
| 每个项目使用同一套大纲 | 架构随问题和证据需求变化 |
| 最后一次性审核 | 逐章审核，必要时重新打开依赖章节 |
| PDF 导出就是终点 | 检查实际页面、分页和目录 |

## 五阶段工作流

`FRAME → RESEARCH → WRITE → REVIEW → PUBLISH`

1. **定义**：明确决策、读者、范围、时间和交付形式。
2. **研究**：建立证据台账、来源链、冲突记录，并主动查找可能削弱当前判断的证据。
3. **写作**：把事实组织成有边界的回答，而不是按来源堆叠摘要。
4. **审核**：逐段、逐章和跨章节复核；前提变化时重新检查后文。
5. **出版**：组装可编辑 HTML，生成 PDF，栅格化页面，并核对目录和版面。

## 三档研究模式

| 模式 | 适合什么情况 | 主要特点 |
| --- | --- | --- |
| **Rapid** | 8–12 页管理层简报、竞品扫描 | 范围聚焦、快速形成架构；不默认启动完整出版审计 |
| **Standard** | 内部行业或公司研究 | 更完整的证据追踪、引用和章节复核 |
| **Publication** | 投资人或公开发布的报告 | 完整证据治理、依赖检查、逐章审核、渲染和出版质量检查 |

## 第一次怎么用

直接告诉 ReportFlow 你要解决的事情，例如：

> 我要给管理层做一份 8–10 页的瑞幸和库迪竞品分析，重点判断我们自己的咖啡品牌应该学什么、哪些不能照搬。

它会推荐 Rapid，只询问会改变研究设计的关键信息，生成研究简报，并围绕“竞品做了什么、为什么有效、哪些做法不可复制”建立章节，而不是套用一份通用行业目录。公开发布的深度研究则选择 Publication，并保留项目状态、证据台账和结论—证据对应表。

## 核心能力

- **研究设计**：从问题、范围和受众出发，生成动态架构，并记录关键决定。
- **证据系统**：维护“结论 → 证据 → 原始来源”链条、冲突记录、反证和披露缺口，避免把试点、订单、交付或收入写成更强结论。
- **逐章审核**：章节门、依赖检查、结论—证据适配和内容价值检查；前提变化时重新打开后续章节。
- **模型与方法选择**：根据研究问题选择方法，分开记录研究、验证和表达方法及其限制。
- **搜索、知识与数据**：搜索服务于问题，证据饱和后停止；验证过的知识可复用，表格和计算保留定义与步骤。
- **出版质量**：检查渲染器、PDF 页数、页面栅格图、全页缩略图总览、长表格、图题、来源和目录页码。

`HTML 正确 ≠ PDF 正确。`  
`PDF 生成 ≠ 出版完成。`

## 输出格式

ReportFlow 当前可以输出：

- **研究简报**：研究问题、范围、重点和证据需求；
- **证据与项目文件**：证据台账、项目状态和关键决策；
- **Master HTML**：正式报告的可编辑出版母版；
- **PDF**：经过渲染、分页、目录和视觉检查的交付版本；
- **PPTX / DOCX**：将已验证的研究结果转换为可编辑演示文稿或 Word 文档。

PPTX 和 DOCX 是研究成果的二次转换，不替代经过验证的研究源文件。

## 适用场景

行业与市场研究、公司研究、竞品分析、市场进入、技术商业化、政策研究，以及需要保留证据边界的投资主题研究。

## ReportFlow 不会替你做什么？

- 为了让报告完整而编造缺失数据；
- 因为某个模型流行就强行使用；
- 把公司宣传口径自动升级成已验证事实；
- 把试点、订单、交付、收入和盈利混为一谈；
- 因为 PDF 成功导出就宣布报告完成；
- 代替研究者完成最终判断。

它不替代专家判断、审计数据、法律意见、学术同行评审或投资顾问，也不适合完全无人值守的高风险决策。

## 安装与快速开始

### 普通用户

将仓库安装为 Codex Skill 后，直接告诉 ReportFlow 你想研究什么即可。它会从研究设计阶段开始，而不是直接生成一篇没有范围和证据记录的长文。

### 开发者与高级用户

```bash
git clone https://github.com/ShuCiYan/ReportFlow-skill.git
cd ReportFlow-skill
python scripts/dependency_check.py <project-state.yaml>
python scripts/discover_renderers.py
```

项目开始时读取 `project/project-state.yaml`；如果不存在，可按 `project/state.template.yaml` 初始化。项目还应维护 `project-manifest.yaml` 和 `decision-log.yaml`。

## Publication Runtime

研究核心不依赖 PDF 渲染器；只有出版 PDF 时才需要运行环境。请阅读 `publication/runtime/README.md`，先检查环境，再在隔离环境中准备 Chromium 和 Poppler。浏览器二进制、缓存和生成的 PDF 不应提交到仓库。

仓库提供 GitHub Actions 的基础测试和出版回归测试，用于在干净环境中验证 HTML、PDF、栅格化页面、全页缩略图总览和目录核对。CI 通过不替代人工视觉检查，但能证明出版链路可以复现。

## 项目结构

```text
SKILL.md                    工作流契约
project/                    项目清单、状态和依赖定义
templates/                  研究简报、证据台账和审核模板
models/                     模型卡和路由建议
methods/                    分析、沟通和验证方法
knowledge/                  知识沉淀与蒸馏规则
data/                       计算清单与数据分析工具
publication/                HTML、PDF、运行环境和出版门
scripts/                    可执行辅助脚本
tests/                      验收与回归测试
.github/workflows/          出版基础测试与回归测试
```
